## 1. Executive Verdict on Architecture ↔ Database Design Consistency

Compared to Version 1.0 (where the Architecture Document omitted PostgreSQL from its C&C and Deployment views, claimed 768-dim `nomic-embed-text` vectors, PBKDF2 passwords, and MD5 deduplication while Database Design Ver 1.0 specified 27 unimplemented tables), **Architecture Ver 1.1 and Database Design Ver 1.1 are now 92% structurally aligned**:
- Both documents agree on the **Multi-Model Storage Architecture (ADR-02)**:
  1. **Host PostgreSQL 15+ (`graph_mind`, port `5432`, accessed via `host.docker.internal:5432` with `SQLAlchemy 2.x Async + asyncpg`)** as the operational System of Record with **13 Implemented MVP tables** and **21 Planned Extension tables**.
  2. **Neo4j Community `5.18.0` (APOC, port `7687` Bolt)** as the Knowledge Graph store with **10 Implemented node labels** (`Customer, SalesOrder, Product, SubCategory, Category, Employee, Document, Clause, Company, Department`), **8 Implemented relationship types** (`PLACED_ORDER, PURCHASED, CONTAINS_PRODUCT, BELONGS_TO, PART_OF, CONTAINS_CLAUSE, PARTY_TO, BELONGS_TO_DEPT`), and **2 Planned labels / 6 Planned relationships**.
  3. **Qdrant `v1.8.2` (port `6333` REST / `6334` gRPC)** as the Semantic Vector Index with **2 Implemented 384-dim Cosine collections** (`cuad_contracts`, `adventureworks_entities`) and **1 Planned collection** (`sop_knowledge_base`), populated by the in-process `SentenceTransformer("all-MiniLM-L6-v2")` embedder and guarded by the **PR1 Layer-1 `is_active` filter**.
  4. **Local Shared Volume (`/data` + `.pending_uploads`)** for raw PDF/CSV/XLSX file persistence (no external Object Storage in MVP).
- Both documents agree on the **Security & Cryptographic Baseline**: `bcrypt` (cost 12) for user passwords, `JWT HS256` with `jti` claim stored in `user_active_sessions` for Single Active Session (`FR59`), 6-digit Email OTP in `password_reset_otps` (`FR60`, noting the unsalted SHA-256 defect in code), Dynamic 2D RBAC Matrix in `knowledge_access_policies` (`FR58`), Read-Only Cypher Guard (`FR61`), and `SHA-256` file content hashing (`BR-06`).

### Remaining Architecture ↔ Database Design Gaps (4 Items)
1. **Lineage Narrative in DB Design Sections 4 & 5 (`E2E-ISS-15`):** `Database Design Ver 1.1` Sections 4 & 5 still narrate cross-model key mapping and Citation Viewer resolution (`GET /citations/{citation_id}`) through `[PLANNED]` tables (`raw_documents`, `entity_extraction_reviews`, `message_citations`, `chat_messages`, `sync_jobs`, `sync_audit_logs`), whereas `Architecture Ver 1.1` (§4.4) describes the actual implemented MVP lineage (`knowledge_upload_approvals` → `pipeline.py` UUIDv5 → Neo4j `:Document/:Clause` + Qdrant `cuad_contracts`, and citations inside `copilot_sessions.messages` JSON).
2. **Backend Module Ownership vs Direct Controller Data Access (`E2E-ISS-12`):** `Database Design Ver 1.1` §2.2 Table 4 maps Application Layer database access to 4 clean services (`Auth & RBAC Service`, `Ingestion & Sync Service`, `Hybrid Query Engine`, `LLMOps & Audit Service`), whereas `Architecture Ver 1.1` §4.2 Table 6.2 reveals that `m2_knowledge_editor`, `m4_decision_support`, and `m5_multifacet_search` are empty stubs and that `main.py` (37 inline routes) and `api/v1/{dashboard.py, sop.py, shift_reports.py}` query PostgreSQL, Neo4j, and Qdrant directly.
3. **Test Verification Status Discrepancy (`E2E-ISS-13`):** `Database Design Ver 1.1` Table 44 marks all 13 implemented PostgreSQL tables as `TEST VERIFIED: NOT VERIFIED`, whereas `Architecture Ver 1.1` (§3.3 Table 5.3, §4.6 Table 6.5, §4.7) explicitly cites the 24 pytest files in `backend/app/tests/`.
4. **Cross-Reference Version & Styling (`E2E-ISS-22`, `E2E-ISS-23`):** `Database Design Ver 1.1` §1.4 P66 still cites `7.C1SE18_Architecture-Document-ver1.0` (instead of `ver1.1`) and §2.2 Table 4 R1 mentions `Tailwind CSS` (removed in `Architecture Ver 1.1`).

## 3. Phase 5.2 — End-to-End Data Flow Consistency Analysis

We traced the 6 primary runtime flows across `User Interface (React 18 + Vite) → API / Controller (FastAPI) → Service / Business Logic → Data Access / ORM / Driver → Database (PostgreSQL / Neo4j / Qdrant) → Response`:

### Flow 1: Authentication, Single Active Session (`FR59`), and Email OTP Recovery (`FR60`)
- **UI → API:** `LoginPage.jsx` / `ForgotPasswordPage.jsx` → `POST /api/v1/auth/login`, `POST /api/v1/auth/forgot-password/{request-otp, verify-otp, reset-password}`.
- **Service → DB:**
  - `auth.py` verifies `users.password_hash` via `bcrypt` (`core/security.py`), issues a JWT (`HS256`) containing a unique `jti`, and calls `session_service.register_user_session(user_id, jti, ip, ua)` which upserts `user_active_sessions` in PostgreSQL and logs to `audit_logs`.
  - Subsequent requests pass through `session_service.verify_active_session`: if `jti != active_session_token_id`, `ConcurrentLoginException` is raised and converted by `main.py` into `HTTP 401 CONCURRENT_LOGIN_KICKED`.
  - `otp_service.py` generates a 6-digit OTP, writes `otp_hash` (`SHA-256`, `expires_at = +300s`, `attempt_count = 0`) to `password_reset_otps`, sends email via SMTP TLS (`:587`), invalidates on 3 failed attempts, and revokes `user_active_sessions` upon password reset.
- **Consistency Verdict:** **Consistent between Architecture Ver 1.1 and Database Design Ver 1.1.** Both documents accurately flag the two code-level defects: `user_active_sessions` uses raw SQL without a physical FK (`E2E-ISS-06`), and `password_reset_otps.otp_hash` uses unsalted SHA-256 (`E2E-ISS-05`).

### Flow 2: Granular 2D RBAC Matrix Configuration & Query-Time Passport (`FR03`, `FR58`)
- **UI → API:** `GranularRbacMatrix.jsx` → `GET / PUT /api/v1/rbac/matrix` (`rbac_matrix_router.py`).
- **Service → DB:** `rbac_matrix_service.py` reads/writes `knowledge_access_policies` (`role_code, department_code, resource_type` → `can_query, can_view_citation, can_edit, can_upload, can_view_sensitive, data_scope`) and writes an immutable entry to `audit_logs`.
- **Consistency Verdict:** **Consistent between Architecture Ver 1.1 and Database Design Ver 1.1**, while both flag the implementation defect (`E2E-ISS-02`) that `knowledge_access_policies.role_code` still uses 4 role codes (`ADMIN, EXECUTIVE, DEPARTMENT_MANAGER, STANDARD_USER`) instead of the 5 BR-04 role codes, and `SRS Final` §4.6 Table T21 uses a different table name (`rbac_permissions_matrix`, `E2E-ISS-01`).

### Flow 3: Staff Document Upload Approval & Multi-Store Ingestion (`FR53–FR54`, `BR-06`)
- **UI → API:** `DocumentsView.jsx` → `POST /api/documents/submit-upload` (`document_approval_router.py`) → stores file in `.pending_uploads` and inserts a `PENDING` row in `knowledge_upload_approvals`.
- **Approval → Ingestion → SSE:** `PendingApprovalsPanel.jsx` → `POST /api/admin/upload-approvals/{req_id}/review` (`action=APPROVE`) → updates `knowledge_upload_approvals.status = 'APPROVED'` → triggers `m1_data_sync/pipeline.py` → computes SHA-256, chunks text, generates deterministic UUIDv5 point IDs and 384-dim `all-MiniLM-L6-v2` embeddings into Qdrant `cuad_contracts`, writes `:Document` / `:Clause` nodes to Neo4j, logs to `audit_logs`, and pushes a realtime SSE event to `useWatcherEvents.js`.
- **Consistency Verdict:** `Architecture Ver 1.1` (§4.4 P192–P193) and `Database Design Ver 1.1` (§3.1.2 Table 14) describe the approval queue accurately, but:
  1. `knowledge_upload_approvals` in code lacks the `sha256_hash` column (`[P]` in DBD Table 14, `E2E-ISS-10`);
  2. `Database Design Ver 1.1` §5.2 Table 75 still describes the ingestion pipeline writing to `[PLANNED]` tables `raw_documents`, `sync_jobs`, `sync_audit_logs`, and `entity_extraction_reviews` (`E2E-ISS-15`).

### Flow 4: Hybrid GraphRAG Query, Dual Safety Guards, RRF Fusion & Citation Viewer (`FR27–FR35`, `FR61`)
- **UI → API:** `CopilotView.jsx` → `POST /api/v1/copilot/chat` (`api/v1/copilot.py`).
- **Service → DB & LLM:**
  1. Loads user's RBAC scope passport (`get_user_scope`).
  2. **Graph Channel:** `nl2cypher_engine.py` + `text_to_cypher.py` generates a Cypher query, validates it through the **Read-Only Cypher Guard (`FR61`)**, injects department scope filters, and queries Neo4j (`:7687`).
  3. **Vector Channel:** Embeds query into 384-dim vector (`all-MiniLM-L6-v2`) and queries Qdrant (`cuad_contracts`, `adventureworks_entities`) with the mandatory **PR1 Layer-1 Guard (`must_not: is_active = False`)** and department filter.
  4. **Fusion & Inference:** `context_fusion.py` merges results via Reciprocal Rank Fusion (`RRF`, $k = 60$) and calls Host Ollama (`qwen2.5-7b-graphmind`, `:11434`), falling back to the Deterministic Fallback in `< 1.0 s` if Ollama times out (`> 30 s`).
  5. **Persistence:** Appends user turn, assistant answer, and citation objects into `copilot_sessions.messages` (JSON) in PostgreSQL.
- **Consistency Verdict:** `Architecture Ver 1.1` (§4.4) matches the source code 100%. `Database Design Ver 1.1` §3.1.2 Table 19 & §3.1.11 P226 accurately document `copilot_sessions.messages` JSON denormalization, while §5.5–§5.6 describe the `[PLANNED]` normalized tables `chat_messages` and `message_citations` (`E2E-ISS-15`).

### Flow 5: Departmental Shift Handover & AI Daily Consolidation (`FR55–FR57`)
- **UI → API:** `ShiftReportEditor.jsx` / `DepartmentReportView.jsx` → `POST / PUT /api/v1/dashboard/shift-reports`, `POST /api/v1/dashboard/shift-reports/{id}/review`, `POST /api/v1/dashboard/shift-reports/consolidate` (`api/v1/shift_reports.py`).
- **Service → DB & LLM:** Writes `DRAFT` / `SUBMITTED` reports with SHA-256 `content_hash` to PostgreSQL `shift_reports` (Table 20); Department Manager signs off (`APPROVED` / `REJECTED` + `manager_comment`); `/consolidate` reads the day's `APPROVED` reports from `shift_reports`, synthesizes a daily Markdown summary via Host Ollama (or rule-based Deterministic Fallback on timeout), and returns it directly to the Web UI.
- **Consistency Verdict:** `Architecture Ver 1.1` (§4.4 P195) and `Database Design Ver 1.1` (Table 20 & Table 42) both consistently note that `shift_reports` is implemented while `shift_daily_summaries` is `[PLANNED]` (not persisted in PostgreSQL, `E2E-ISS-09`).

### Flow 6: AEGIS Workstation Heartbeat, 2-Phase Sync Mode & Emergency Kill Switch (`FR13–FR14`, `FR62`)
- **Daemon / UI → API:** `aegis_file_watcher` & `WorkstationsPanel.jsx` → `/api/v1/workstations/*` (`api/v1/pb56_workstations.py` → `pb56_workstation_service.py`).
- **Service → DB:** Persists workstation state and 30s heartbeats in `pb56_workstations` (Table 15), idempotent sync reports in `pb56_workstation_sync_logs` (Table 16), and 2-phase command state transitions (`REQUESTED → APPLIED/CANCELLED/REJECTED`) in `pb56_sync_mode_audit_logs` (Table 17).
- **Consistency Verdict:** **100% Aligned** between `Architecture Ver 1.1`, `Database Design Ver 1.1`, and Source Code (whereas `SRS Final` §4.5 still claims a `WSS` channel and omits the `pb56_*` tables from §4.6, `E2E-ISS-01` / `E2E-ISS-18`).

## 4. Phase 5.3 — Architectural Responsibility vs Data Responsibility Assessment

| Evaluation Dimension | Assessment | Findings & Evidence |
|---|---|---|
| **Single Source of Truth (SoT) Partitioning** | **GOOD** | Both `Architecture Ver 1.1` (`ADR-02`) and `Database Design Ver 1.1` (§2.1 Table 3) strictly partition operational/ACID data into Host PostgreSQL, relational business knowledge into Neo4j, and derived 384-dim semantic chunks into Qdrant. |
| **Layer Separation (Controller vs Service vs Data Access)** | **NEEDS IMPROVEMENT** | `m1_data_sync`, `m3_hybrid_copilot`, and `m6_admin_security` maintain clear service/module boundaries, but `m2`, `m4`, and `m5` are unextracted stubs (`E2E-ISS-12`), causing `main.py` and `api/v1/{dashboard.py, sop.py, shift_reports.py}` to execute database queries directly inside route handlers. |
| **Schema Lifecycle & Migration Governance** | **NEEDS IMPROVEMENT** | `Database Design Ver 1.1` §5.8 and `Architecture Ver 1.1` §4.7 identify that 5 backend files execute `CREATE TABLE IF NOT EXISTS` at runtime and Alembic migrations are out of sync with the 13 implemented tables (`E2E-ISS-06`). |
| **Read/Write Access Control & Safety Guards** | **GOOD (with 1 Role-Code Gap)** | Read-Only Cypher Guard (`FR61`) on Neo4j and PR1 Layer-1 `is_active` Guard on Qdrant are enforced server-side. However, `knowledge_access_policies` in PostgreSQL must split `ADMIN` into `IT_ADMIN` and `KNOWLEDGE_MANAGER` to enforce `BR-04` at the database policy matrix level (`E2E-ISS-02`). |
